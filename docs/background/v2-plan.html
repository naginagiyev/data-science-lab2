The plan in one page

If you read only one section, read this one.

When tables are messy, an agent that uses the LLM to understand and repair the data, and uses tested code to verify every step and train the model, builds better models than classical AutoML. It is also more reliable and cheaper than agents that write free code. When tables are clean, it is not worse. This is your main hypothesis. Your experiments will test it. Do not write it as a fact until the numbers support it.
The niche

Messy, real-world tables

Business data is full of numbers stored as text ("8GB", "$1,250"), typos in categories, fake missing values (-999, "?"), ID columns and leaky columns. Classical AutoML assumes that someone already cleaned the table.

The idea

The LLM proposes, the code verifies

The LLM reads the columns like a data scientist. It picks cleaning steps from a fixed toolbox of tested operations. Code checks each step and builds one leak-free scikit-learn pipeline. It keeps the steps only if validation shows they help.

The engine

Modelling is not the LLM's job

A proven engine trains the model: LightGBM or CatBoost with Optuna, under a time budget. AutoGluon can plug in instead. The LLM never writes training code and never sees the test set.

The proof

A messy-table benchmark

Take clean datasets and add controlled mess at several levels. You know the truth, because you made the mess. Add leaky columns and some naturally messy datasets. Compare with AutoGluon, FLAML, skrub, LightGBM, your v1 and one or two LLM agents. Measure score, success rate, time and cost.

The timeline

Two semesters

Now: rebuild the core, build the benchmark, get first results on about 15 datasets, write a paper-style report. Next: scale up, run ablations, try more LLMs, release the code, write the thesis and a workshop paper.

What you will not claim

  • That you beat AutoGluon on clean, well-prepared tables. You probably won't, and you don't need to.
  • That you win Kaggle or MLE-bench. Big labs compete there with 24-hour GPU runs.
  • Images, text-only data, time series or clustering. Only tabular binary, multi-class and regression. You already narrowed the scope in your last commits, so keep it that way.

How examiners and reviewers read your work

They look for four things: (1) a clear question; (2) a fair comparison with strong baselines; (3) enough repetitions and a statistical test, so that the result is not luck; (4) ablations that show why it works. DS Lab 1 had none of these (A1). This plan builds all four.

The market today

Five families of tools try to automate ML on tables. Each one is strong at something and weak at something else. Your thesis sits in the space between them.

FamilyExamplesStrong atWeak at
Classical AutoML AutoGluon, FLAML, auto-sklearn, H2O AutoML, TPOT Very strong and reliable on clean tables. Searches many models, tunes them and builds ensembles. AutoGluon is near the top of current tabular benchmarks (TabArena). Does not understand meaning: "8GB" is a category, not the number 8. It cannot know that refund_issued is a leak, and a leak even improves its validation score. It assumes the table is already clean.
Tabular foundation models TabPFN (Nature 2025, newer versions since), TabICL Excellent accuracy on small and medium tables in seconds, with no tuning. The same blindness to meaning. They need a clean table and have size limits.
Code-writing LLM agents AIDE, DS-Agent, Data Interpreter, AutoKaggle, AutoML-Agent, iML Read the data like a human. Flexible: they can write any Python. Free code crashes in new ways on every dataset. Results vary between runs. ML code from LLMs often leaks. Many LLM calls cost money. They are tested mostly on Kaggle-style competitions (MLE-bench).
LLM + AutoML hybrids AutoGluon Assistant (MLZero), LightAutoDS-Tab Use an AutoML library as the engine, so they are stronger and more reliable than pure code agents. From what I found, their papers test competition-style and multimodal tasks. They do not measure what happens when the table itself is messy or leaky.
LLM data cleaning Bendinelli et al. 2025, AutoDCWorkflow, CleanAgent, LLMClean, ProfiliTable Show that LLMs can find and fix many data errors. Stop at cleaning. Most do not train a model end to end or compare against AutoML.

MLE-bench (OpenAI, 2024) is the main benchmark for LLM agents. In the original paper, the best setup won a medal in about 17% of Kaggle competitions. In 2026, systems such as iML report about 45%. That race moves fast and needs a lot of compute, so don't run it. Pick a different question.

What my search found (October 2026)

I looked for work that tests agents end to end on messy tables (raw messy table → cleaning → model → score) against classical AutoML, and I did not find any. The closest works:

  • Bendinelli et al. (ICLR 2025 workshop). An LLM agent cleans a corrupted training set, but the model and the features stay fixed.
  • Budach et al. (2022). They measure how data errors hurt ML models, without any LLM.
  • ProfiliTable (2026) and AutoDCWorkflow (2024). They clean tables but do not train models.

This is a strong sign that the gap is real, but a web search is not proof. In weeks 1–2, read the papers in the reading list and confirm it.

Why not just let an LLM agent write all the code?

It crashes

Free code fails in new ways on every dataset. Your v1 needed up to 10 repair rounds per stage and still failed sometimes.

It leaks

LLM-written ML code often fits a scaler before the split or tunes on the test set. A 2025 study also found that LLMs often fail to notice these mistakes in code. Your v1 had both problems (B1, B2).

It varies

Two runs on the same data can give very different pipelines and scores.

It costs

Many long LLM calls per dataset. Your v1 made up to about 60 calls per run.

Your hidden advantage

You know these failure modes from your own DS Lab 1 code. In the thesis you can describe them with real examples (overview.md is already that list). Few papers explain why agents fail. You can.

Your position: LLM proposes, code verifies

Place the five families on two axes. On one axis: does the tool understand what the data means? On the other: is it reliable, verified and leak-free? The top-right corner is empty. That is your target.

This is my qualitative reading of the field, not measured data. Your literature review should confirm it.

In simple words: LEGO versus clay

A code-writing agent sculpts the pipeline from clay every time. Anything is possible, but it often collapses. Your agent builds with LEGO blocks instead. You write and test each block (an "operation") once, and the LLM only decides which blocks to use and with which settings. For rare cases there is still a little clay (sandboxed custom code), but it must pass tests before you use it.

LLM does
  • Picks the target and task type when they are unclear
  • Explains what each column means
  • Spots units, currencies, dates, spelling variants and fake missing values
  • Judges: "Is this value known at prediction time?"
  • Chooses toolbox operations and fills in their parameters
  • Repairs one operation from a short, structured error
  • Proposes new features (semester 2)
  • Writes a short summary of the run
Code does
  • Reads files, profiles data, splits rows
  • Applies operations and checks the result
  • Measures statistical evidence of leakage
  • Cross-validates, and keeps or rejects LLM proposals
  • Searches and tunes the models
  • Uses the test set once
  • Logs every decision and every LLM call
  • Saves one model file and a report

Is it still "agentic"? Yes. The agents make decisions, use tools, look at validation results and revise their plan. The difference is that the tools are tested and every decision is checked. This is a workflow with agent decisions at fixed points, which is more reliable than a free loop. Your thesis can argue for this design with data (see the "free code" ablation).

The new architecture

This part describes v2. Every design rule comes from a problem you already found in DS Lab 1.

Design principles

Eight rules. When you are unsure how to build something, come back here.

Rule 1

LLM proposes, code verifies

The LLM never decides something that code can check: types, nulls, exit codes, whether a file exists, scores.

fixes C1
Rule 2

Typed actions first, free code last

The LLM fills in a typed plan using the toolbox. Free code is a rare escape hatch, and it always runs in a sandbox.

fixes fragilityD2
Rule 3

Leak-free by construction

Split first. Every step that learns from data is a scikit-learn transformer fitted on training rows only. The test set is touched once.

fixes B1B2B3
Rule 4

Every stage has a fallback

If the LLM fails, a rule-based default takes over. A run always ends with a model and a report.

fixes fragilityE5
Rule 5

Fixed rules, decided in advance

The metric (chosen by task type), the time budget, the seeds and the splits come from settings, not from the LLM.

fixes B7
Rule 6

One run = one folder

All inputs, decisions, LLM calls, models and scores go to runs/<id>/. Runs never overwrite each other.

fixes E2C3D4
Rule 7

Budgets everywhere

Each stage has a time limit, and each run has a maximum number of LLM calls and a maximum cost. When a budget runs out, the fallbacks take over.

fixes costB5
Rule 8

Same code for demo and benchmark

One entry point. The benchmark calls the same function as the command line.

fixes E1

03

Frame the task

LLMuser can overridefixes B7 · B8

Decide the target, the task type, the metric, the ID columns and the time column (if there is one). This replaces targetdetector.py, infer_task_type_from_target() and configfiller.py.

  1. Code ranks target candidates: name hints, position, not an ID, not constant, cardinality.
  2. The LLM chooses from the top candidates and returns a confidence and a reason (structured output).
  3. Rules propose the task type. The LLM may override them in unclear cases, such as an ordinal 3–8 target, but it must give a reason.

  5. Command-line flags (--target, --task) override everything. In --ask mode, the user confirms when the confidence is low.

Input

You can measure this stage for free. OpenML stores the true target of each dataset ("default target attribute"), so you can report framer accuracy on 100+ datasets. That is a small, clean result for your report.

08

Compile and check

Deterministiccustom ops sandboxedfixes C1 · B1

Code validates the plan with Pydantic and builds one scikit-learn Pipeline: the agent's operations followed by a generic stage. It fits the pipeline on the training folds and runs data checks.

Data checks (deterministic; they replace the LLM judges)

  • Output columns have the expected types. No infinite values. No column became all-missing.
  • No rows are lost.
  • The transform also works on unseen rows (the validation fold), not only on the rows it was fitted on.
  • It finishes within the time limit.

Repair

If an operation fails, the LLM gets a short, structured error, for example: parse_unit on Weight: 3% of values could not be parsed, examples: "1.3 kgs", "?". It may fix that one operation. After 3 failed repairs, the operation is dropped and logged.

Input

plan.json, training folds

Output

A checked pipeline + a check report

If it fails

Drop the broken operations and keep the rest.
09

Validation gate

DeterministicLLM refinesnew

Code compares two pipelines on the same CV folds with the same quick model (for example, LightGBM with default settings): generic only versus agent + generic. The agent pipeline is kept only if it is not worse, within a small tolerance.

  1. Refine. The LLM sees the per-fold results and may revise the plan once or twice. This is where the agent learns from feedback.
  2. The generic stage always runs last: imputation, category encoding, simple date parts, and turning text into features. One option is to use skrub's TableVectorizer here. Then your "no LLM" ablation is exactly the skrub baseline, so every gain you show comes from the LLM itself.

Important subtlety

The gate does not decide on leak removals. Removing a leak lowers the CV score, because the leak was "helping". If the gate decided, it would always keep the leak. Leak decisions use the leakage guard only.

Why this is leak-free. Parsing operations learn nothing from the data. Operations that do learn something (the category map, text features) learn it only inside fit(), on training rows. At prediction time, unseen values become "other" or missing.

Rules for the custom escape hatch

  • It must be one class with fit() and transform(), written by the LLM from prompts/customop.md.
  • It runs in a separate process with a time limit, in a temporary folder, with no API keys in the environment (D2).
  • It is tested on a training sample first and then on unseen rows. Only after that may it join the pipeline.
  • After 3 failed repairs it is dropped. Report how often custom was needed. If it is needed often, that is a sign you should add a new toolbox operation.

The leakage guard

Leakage is the most dangerous mistake, because it makes results look better. Classical AutoML cannot see it, because a leak improves the validation score. Your agent combines three kinds of evidence.

Statistical (code)

One column alone predicts the target almost perfectly (for example, single-feature CV AUC above 0.98 or R² above 0.95). A column equals the target, or a simple function of it. Missing values appear in only one class.

Semantic (LLM)

"Would this value exist at the moment of prediction?" Examples: refund_issued when predicting fraud, cancellation_date when predicting churn, final_grade when predicting pass/fail.

Structural (code)

ID-like columns, row numbers (Unnamed: 0), and timestamps after the event.

EvidenceAction
Semantic + statisticalDrop the column. Report it as "leak removed".
Strong semantic onlyDrop and report. In --ask mode, ask the user first.
Statistical onlyKeep, but report a warning: "suspiciously strong, please check".
NoneKeep.

The thresholds are settings. Tune them on a separate set of datasets, never on the benchmark you report.

The LLM layer

Merge llms/codex.py and llms/generation.py into one small client, llms/client.py. Every agent calls the LLM through it.

  • One function, roughly ask(prompt_name, inputs, schema), that returns a validated Pydantic object.
  • Model name, temperature (0 or low) and seed come from settings and are never hardcoded (C3).
  • Retries. API errors are retried with backoff (tenacity). If the answer does not match the schema, ask again with the validation error, at most 2 times.
  • A disk cache keyed by model + prompt + inputs. Re-runs are free and identical, and tests can replay real answers without calling the API.
  • Every call is logged to runs/<id>/llm.jsonl: stage, prompt name and version, tokens, latency, cost, success.
  • A budget guard. When a run reaches its call or cost limit, the agents return "no answer" and the fallbacks take over.
  • Prompts stay in prompts/*.md, but the lists inside them (operations, metrics) are injected from code (C4).
  • Semester 2: add a second provider, or a local model, for RQ6.

Fairness rule

In every comparison, use the same LLM for your agent and for the LLM baselines. While you develop, use a cheap model and the cache.

Part 4

Proving it: evaluation

This is the part that turns a tool into a thesis.

Benchmark design

You need a test where you know the truth. The trick: start from clean datasets, add realistic mess with a generator that remembers what it changed, and see which tools recover. Then add naturally messy datasets, so that nobody can say "it only works on synthetic mess".

Group A

Clean base datasets

15 now, 30 later, from OpenML or TabArena. 1k–100k rows; binary, multi-class and regression. They need readable column names, because the LLM needs meaning. Skip datasets with names like V1, V2, except as "no harm" controls. Prefer less famous datasets, because an LLM may have memorised Titanic or Adult.

Group B

Controlled mess

Group A plus the mess generator: 12 types × 4 levels (0 = clean, low, medium, high), with fixed seeds and saved ground truth. This gives your main figure: score versus mess level.

Group C

Naturally messy

5–10 real datasets, for example laptop prices, used cars, Airbnb listings, skrub's employee salaries, and your own ibmchurn and kinghousedata. Check each license.

Group D

Leakage set

About 10 datasets where you add 1–2 realistic leaky columns by hand (with names like refund_issued), documented in a table. At test time, set the leaky column to missing, because in real use that information does not exist yet.

Protocol: the fairness rules

  • All systems get the same train/test files for each dataset and seed. No system sees the test labels; the harness scores the predictions.
  • Same time budget (10 minutes in semester 1, 30–60 minutes in semester 2), same machine, and the same LLM for every LLM system.
  • 3 seeds in semester 1, 5 in semester 2. Report mean ± std.
  • The metric is fixed per task: ROC-AUC (binary), log-loss (multi-class), RMSE (regression).
  • If a system fails, it gets the dummy model's score for that run, and the failure is counted. The AMLB benchmark handles failures the same way.

Types of messy data

Each type must be realistic, reversible (so that you know the truth) and controllable by a level. The last row is a control: classical AutoML already handles plain missing values, so the agent should not gain anything there. Honest controls make your other results believable.

Metrics and statistics

What you measure
  1. Model quality: the primary metric per task, then a normalized score.
  2. Reliability: success rate (valid predictions within the budget) and std across seeds.
  3. Cost: wall-clock minutes, LLM calls, tokens, $.
  4. Decision quality: framer accuracy, leak detection precision and recall, repair accuracy (did the agent restore the true values? You can check, because the generator saved them), and the share of LLM operations the gate accepted.
How you compare, in simple words
  • Normalized score = (score − dummy) / (best − dummy) for each dataset. 0 means useless and 1 means the best result seen. This lets you average over datasets. For "lower is better" metrics such as log-loss and RMSE, flip the direction first.
  • Average rank: rank the systems on each dataset (1 = best), then average.
  • Critical-difference diagram: one picture that shows the average ranks and which systems are not significantly different (Friedman test + Nemenyi test). It is standard in AutoML papers.
  • Wilcoxon signed-rank test: answers "is my system better than AutoGluon over many datasets?" and checks that the wins are not luck. p < 0.05 is the usual line.
