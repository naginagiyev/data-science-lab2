1. The problem: messy tables

AutoML tools such as AutoGluon or FLAML are very good on clean tables. Real tables are rarely clean. Numbers are stored as text with units, dates have many formats, one category has many spellings, unknown values hide behind "-999", and some columns even leak the answer. A normal AutoML tool reads such columns as text categories and cannot use the numbers inside them.

To test this in a fair way, the project has a corruptor: it takes a clean table and adds mess of 12 types at 4 levels (0 = clean, 3 = very messy). It also writes the true value of every changed cell, so we can later check whether a cleaner restored it. These are real examples from the benchmark files:

2. The idea: the LLM proposes, code verifies

Earlier agents (including v1 of this project) let the LLM write whole Python scripts. That crashed often, leaked test data, and cost a lot. v2 is different: the LLM can only choose operations from a fixed catalog (for example parse_units, extract_pattern, map_categories) and fill in their parameters as structured JSON. Every proposal then has to pass several checks written in normal code:

Typed operations

18 tested operations (parse numbers, units, dates, booleans, split packed values, fix spellings, missing values, rare categories, text features, row and target rules). Each one learns only from training rows.

Fallbacks everywhere

If an LLM call fails or gives a bad answer three times, a rule-based answer is used. Every run therefore ends with a model and a report.

3. How v2 works: the 12 stages

One function runs the whole pipeline, both for a normal user ("demo mode") and in the benchmark. Purple boxes use the LLM, green boxes are code checks, orange is the model training.

What a run produces

Each run writes a folder with report.md (task, split, audit issues, leak decisions, the plan and each step's effect, scores next to a dummy model, time and cost per stage), decisions.jsonl, llm.jsonl, plans.json, gate.json and model.joblib. The saved model predicts directly from new raw files in the same messy format.

The baselines are the dummy model (predicts the mean or class shares), LightGBM with default settings, skrub (a tool built for dirty tables), FLAML and AutoGluon (a top AutoML system). Every system gets the same files, the same 120 seconds, 4 CPU threads, and never sees the test labels.

5. Safety nets

The validation gate

The gate compares P0 (only the safe, protected steps such as dropping ids) with P1 (all steps) by cross-validation. Each risky step is tested by leaving it out. A step that makes the score worse is removed; an untested drop is never applied.

The leak guard

A column is dropped as a leak only with evidence: structural (an id), statistical (it predicts the target too well) and semantic (its name means "after the event", judged by the LLM).

Budgets and caps

Every stage has a time limit; the LLM client stops at a per-run and a global dollar cap ($5 for the whole project). A spend ledger records every paid call.

Sandbox for generated code

Code written by the LLM (the custom step and the freecode variant) runs in a separate process: import checks, a time limit, a temporary folder and no API key.

Development tuning found real bugs

Before the experiments, v2 was tuned on a separate development pool (never used for results). The first round showed that rules was worse than generic on some messy files. Reading the decision logs found the causes: packed values were mistaken for id columns and dropped, money signs like "39 USD" were not parsed, "1.6k / 0.0007M" suffixes were skipped, and a time limit starved the model search. 7. The benchmark

Group A + B: controlled mess

15 clean OpenML (TabArena) datasets, 6 binary, 3 multi-class, 6 regression; the corruptor adds mixed mess at levels 0–3, 3 seeds. 180 files plus 165 single-type files.

Group C: natural mess

5 datasets that are messy in their original form, as a check outside our own corruptor.

Group D: leakage

10 datasets with one realistic leak column each; the test file has the leak masked (deployment) and a naive copy keeps it.

Fair protocol, written down first

The pilot datasets, hypotheses, metrics and "what counts as support" were pre-registered and tagged in git before any pilot run; the code was frozen; later changes are in docs/deviations.md.

The normalized score used in most charts puts every cell on the same scale: 0 = as good as the dummy model, 1 = as good as the best system in that cell. A failed run counts as 0.

9. Results: leaks

A leak column contains information that is only known after the outcome (for example a refund for a churned customer). A model that uses it looks perfect in testing and fails in real use. In the leak experiment the test file comes in two copies: a naive one that still has the leak values, and a deployment one where they are masked.

v2 full found 5 of 5 leak columns with 0 false drops. v2 rules (no LLM review of column meanings) found 0 of 5: the meaning of a column name is where the LLM helps most.

10. Results: which parts matter (ablations)

At level 3 on 4 datasets, every v2 variant that has a cleaning stage scores far above the tools without one. Removing single parts (review, gate, repair, value samples) or letting the LLM write free code changes little on this small sample.

Cost, time and reliability

Large files work too: the full credit-card fraud file (creditcardfraud, 284,807 rows) finished in 286 s with 2.14 GB peak memory, and a 1,000,000-row file in 267 s with 1.35 GB, both inside a 300 s budget.

13. The auditor (edatool)

edatool finds the data problems that the cleaner then fixes. It was improved in this project (new detectors for units, mixed units, packed values and date formats) and measured on its own injection benchmark against three other tools.

14. Projection: is the full benchmark worth running?

The pilot is small. The projection estimates what a full benchmark (15 datasets × 3 seeds) would show. It simulates the pre-registered test 2,000 times using the effects and the noise seen in the pilot. A power of 0.8 means an 80% chance of a clear result.

Was the projection reliable? The held-out check

Before running 4 held-out cells, their scores were predicted and the predictions were committed to git. 3 of 4 fell inside their interval, so the projection passes its own check.

Recommendation: do not run the full benchmark as it is yet. With the current effects it would likely not give a clear answer for v2 full vs AutoGluon (power 0.28). First fix the two weaknesses below (they cost v2 two runs), then run a reduced benchmark: the leak grid and the plug-in comparison (v2 + AutoGluon vs AutoGluon, power 0.68).

15. Weaknesses and limitations

Time limits not enforced when time is gone

When the audit takes long, later stages still do their work although their time is used up. This caused 2 of the v2 full runs to be killed (counted as failures, as pre-registered). Fix is simple; it was found after the freeze, so it was not applied.

Decimal commas in the target

A regression target written as "39,6" is not converted, so v2 failed on 3 of the 15 layout files.

Small pilot

8 datasets, one seed for the LLM systems, 120 s on an emulated laptop CPU. The effects are uncertain; the projection says so.

Other limits

The controlled mess comes from our own corruptor; no gain on natural mess; impossible values are not detected; the gate is noisy on very small tables; the sandbox is a safety net, not a security boundary.

Skipped on purpose: TabPFN (its weights need a login), v1 and AIDE (the plan does not run code-writing agents), and the full benchmark grids (written and checked, left for later).
